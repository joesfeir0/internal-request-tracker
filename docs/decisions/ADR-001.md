# ADR-001: Keep status history, not only the current status

Status: accepted
Date: 2026-08-31
Related files: product-spec.md, architecture.md, data-model.md

## Problem

A request changes status many times before it is closed. The product must be able to show how it changed, not only where it is now.

product-spec.md says every status change must be saved with who made it and when. It also says the history can be added to, but never edited or deleted. architecture.md repeats this as R8 and says it applies to everyone, including handlers.

The model therefore needs to decide how to store status. We cannot recover missing history later: once an old status has been overwritten, that value is gone.

## Options

**Option A: keep only the current status.**
The Request holds one status value. Each change writes over the last one.

This is the simplest option. But it can only answer "what is the status now". It cannot answer "when did it become In Progress" or "who rejected it", because the old value no longer exists. That fails FR-10 and the auditability requirement.

**Option B: keep only the history.**
Save every change as its own record. Work out the current status by finding the newest one.

No history is lost, and the events are the only place that defines the current status. But reading a list of requests becomes slow, because the product has to find the newest event for every request in the list before it can show anything. That is the most common action in the product.

**Option C: keep both.**
The Request holds its current status. Every change also creates a Status Event with the new status, the person, and the time.

## Decision

I chose Option C.

Option A was never really possible, because FR-10 and the auditability requirement need the history. Between B and C, I chose C because it makes the most common request-list query fast.

Storing the current status duplicates information the system could work out from the events. I accepted that trade-off on purpose.

## Consequence

**What I gain.**
The product can say when a status changed and who changed it. The history is only added to, so it stays trustworthy. Reading a list of requests is fast, because each request already knows its own status.

**What it costs.**
The same fact is now stored in two places, so they could disagree. Events are never deleted, so this data keeps growing for the life of every request. The model is more complex than storing only one status value.

**What the rest of the system must now do.**
The current status and its Status Event must be saved together, or neither is saved. If only one is saved, the data is wrong without a visible warning. That makes this the most dangerous failure here. architecture.md already lists this failure and gives the same rule, so the two files agree.

Nothing may edit or delete a Status Event. The backend gives no way to do it, and no role is allowed to.

Implementation scope: this rule applies to application actions and API routes. The local demo reset utility can delete test records and history; the database does not itself make events immutable against maintenance access. Storing current status avoids deriving it from history, but the current list endpoint also loads history and comments. This ADR's performance rationale is not a measured performance result.

**When to look at this again.**
If the number of events becomes a real problem, the question to ask is how to store old events, not whether to keep them.
