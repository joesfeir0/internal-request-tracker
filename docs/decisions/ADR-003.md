# ADR-003: Demo identity with one server-side permission policy

Status: accepted
Date: 2026-09-26
Related files: architecture.md, department-workflow.md, week5-release-operations.md

## Problem

The Week 1 architecture assumed users sign in through the organization's Identity Service (decision D2). That service does not exist for this project. The live app must still show who is acting, what each person may do, and that forbidden actions are rejected. Before this decision, permission rules also lived in two places: the backend enforced them, while the frontend repeated its own copies (for example checks for the hard-coded ID `employee-001`), so the two could drift apart.

## Options

**Option A: build a real login system** (accounts, passwords, sessions). Not required: the Day 15 handoff asks for "demo access / identity" and lists enterprise SSO as a non-goal. It adds scope before the deadline without changing the permission rules.

**Option B: keep the teaching identity from Week 3** (Day 8: "a teaching identity, not a login system"). The browser sends `X-Actor-Id`; the backend looks the ID up in a fixed directory and ignores any role the browser claims.

**Option C: B, plus one permission policy shared by enforcement and the UI.** The backend decides every permission in one file and tells the UI which actions are allowed for each request.

## Decision

Option C.

- **Identity:** six demo accounts in [`dev-actor.ts`](../../backend/src/requests/dev-actor.ts): two employees (Maya, Karim) and four handlers (two IT, one HR, one Finance), served to the UI by `GET /actors`. Unknown IDs get 401.
- **Permissions:** [`policy.ts`](../../backend/src/requests/policy.ts) defines view, claim, reply and status-change rules. The service enforces them (404 for requests you may not see, 403 for forbidden actions, 409 for invalid states), and every response carries `allowedActions` computed by the same functions for the calling account.
- **UI:** shows only the actions in `allowedActions` and explains why others are missing. It never decides a permission itself.
- **Boundaries visible in the UI:** "Open by reference" asks the server directly, so another employee sees the real 404; a second IT handler shows that only the assignee can change status.

## Consequences

**Gained**

- One source of truth: the UI cannot offer an action the server would refuse.
- Allowed and rejected actions can be demonstrated from the live app, not only with API tools.
- Replacing the demo identity with real sign-in later changes only how the actor is resolved; the policy stays.

**Costs and limits**

- **Anyone with the URL can choose any demo account.** This is acceptable only because all data is fictional and the app is labelled as a demo. It is not suitable for real employee data.
- Identities and department memberships are fixed in code, not managed in a directory.

## When to revisit

Before any real employee uses the system: put the organization's sign-in in front, resolve the actor from a verified session instead of a header, load memberships from a trusted directory, and add offboarding.
