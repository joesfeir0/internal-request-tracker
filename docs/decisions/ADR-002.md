# ADR-002: Host on Render with PostgreSQL on Neon, at no cost

Status: accepted
Date: 2026-09-26
Related files: week5-release-operations.md, architecture.md, data-model.md

## Problem

The final submission must be a live app that reviewers can open without the student's laptop being on, and it must stay reachable through the defense. The owner's constraint is **zero cost**. Until now the app stored data in a SQLite file next to the backend and ran only on the laptop.

Free web hosts give the app a disposable disk: it is reset on every restart, redeploy or wake-up from sleep. A SQLite file there would silently lose every request, which is a hard failure ("persistence broken").

## Options

**Option A: keep SQLite and host it on a free web service.** Simplest code, but the file disappears with the disk. Rejected.

**Option B: SQLite on a paid persistent disk.** Works technically, but breaks the zero-cost constraint.

**Option C: free web service + separate free managed PostgreSQL.** The app can restart as often as the host likes; the data lives elsewhere.

For option C, the choices compared were:

| Choice | Why it was or was not chosen |
| --- | --- |
| Render free web service | Chosen. Free Node web service with HTTPS, deploys from GitHub. Suggested in the Day 15 handoff. Sleeps when idle. |
| Railway | Not chosen: no permanent free tier, only trial credit. |
| Render free PostgreSQL | Not chosen: free databases expire after a limited period, possibly before the defense. |
| Supabase free PostgreSQL | Not chosen: free projects are paused after about a week without activity and must be restored by hand. |
| Neon free PostgreSQL | Chosen. The project stays available; idle compute sleeps and wakes automatically in about a second. Branches give separate `development` and `production` databases. |

## Decision

Option C: **one Render web service** runs the NestJS backend and serves the built React app on the same address; **Neon PostgreSQL** stores the data; Gemini stays the AI provider.

Prisma stays; only its database provider changed from `sqlite` to `postgresql`, with one fresh baseline migration. The SQLite migrations remain in Git history.

## Consequences

**Gained**

- Data survives restarts and redeploys; the laptop can be off.
- One address for frontend and API: no CORS, no development proxy in production, no build-time API URL.
- Separate branches keep development and live data apart.
- Development and production use the same database engine, so fewer surprises at deploy time.

**Costs and limits**

- Free-tier behavior: the app sleeps after ~15 minutes idle and takes up to ~1 minute to wake; Neon has monthly compute and 0.5 GB storage limits. Disclosed in the README; no uptime promise.
- Local development and tests now need a PostgreSQL address (a Neon branch or local PostgreSQL) and are slower over the network.
- Neon becomes a dependency: if it is unreachable, `/health` reports `unhealthy` and the core journey stops.
- Frequent database checks would keep Neon awake and use its free compute, so the platform's own health check uses `/health/live`, which does not touch the database.

**What the rest of the system must now do**

- Refuse to start without `DATABASE_URL` instead of falling back to a local file.
- Keep migrations (safe, used by deploys) separate from seeding and reset (never part of a deploy; reset refuses a remote database without `--confirm-remote`).
- Give each test its own schema and drop it afterwards.

## When to revisit

If the app needs guaranteed availability, real employee data, or more than the free allowances, move to paid tiers or the organization's own hosting. The code does not change: only the database address and host configuration do.
